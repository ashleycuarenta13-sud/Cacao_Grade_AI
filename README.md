## The five actors

The document's Part A lists five roles; all five exist as rows in the `roles` table and
are enforced at the API boundary.

| Actor | Slug | May classify | Batch history | May delete batches |
|---|---|---|---|---|
| Farmer | `farmer` | yes | own only | own only |
| Cooperative staff | `staff` | yes | every batch | any batch |
| Buyer | `buyer` | **no** | every batch | **no** |
| Agricultural extension worker | `extension_worker` | **no** | every batch | **no** |
| Administrator | `admin` | yes | every batch | any batch |

Registration always creates a `farmer` account. An administrator promotes or demotes an
account through the **User Management** screen, which calls
`PATCH /api/admin/users/{id}`. The endpoint accepts either the slug (`extension_worker`)
or the document's actor name (`Agricultural Extension Worker`), refuses an unknown role,
and refuses an administrator demoting their own account.

## Part D: request-to-response trace

| Step | Component | Implementation |
|---|---|---|
| 1 | Farmer selects/captures a photo | `farmer_dashboard.dart` → `_Classify._pick()` |
| 2 | Client validates type and size | same file — JPG/PNG, 5 MB limit |
| 3 | Flutter POSTs the photo + auth token | `CacaoApi.classify()` → `POST /api/classify` (multipart + bearer) |
| 4 | API verifies the token and the role | `classify_image()` — 401 without a session, 403 for non-submitters |
| 5 | API validates and stores the photo | `backend/uploads/`, served back through `GET /uploads/{name}` |
| 6-7 | API forwards to the CNN service | `CNN_SERVICE_URL` → `POST :8001/predict` |
| 8 | Business logic + SQL INSERT | `QUALITY_NOTES`/`RECOMMENDATIONS` + `save_classification()`, linked to a `batches` row |
| 9 | API returns the JSON payload | `{id, batch_id, predicted_class, confidence, quality_notes, recommendation, image_url, engine}` |
| 10 | Flutter updates state and renders | `_submit()` → `ref.invalidate(serverBatchesProvider)` → `_resultCard()` |

## About the model — and the dataset you still need

`cnn_service/` loads a trained model from `cnn_service/model/` when one is present:

```
cnn_service/model/cacao_model.keras    (or .h5, or .onnx)
```

Until then it runs a **deterministic colour-statistics baseline** (lightness + redness
ratio → Gaussian → softmax) so the whole pipeline stays runnable end to end.
**That baseline is not a CNN.** After you drop a real model in and restart the service,
`GET /health` reports `"engine": "cnn"`.

### What the loader expects

| Property | Value |
|---|---|
| Input size | **224 × 224** |
| Channels | **RGB** (JPEG/PNG decoded with Pillow) |
| Normalisation | pixels **÷ 255.0**, `float32` |
| Output | 4 scores, softmaxed |
| Class order | `unfermented`, `partially_fermented`, `well_fermented`, `over_fermented` |

### Building the dataset

You need cut-test photographs, **one label per image**, four classes. A workable minimum
is roughly **150–300 images per class** (600–1,200 total); below that, use transfer
learning with heavy augmentation or the model will not generalise.

1. **Produce real cut tests.** Take a pod, cut ~10 beans in half across the middle, and
   photograph the cut faces together on a neutral (white or grey) tray.
2. **Label by fermentation day**, which is the standard proxy used in the literature:
   | Days fermented | Class |
   |---|---|
   | 0 | `unfermented` |
   | 1–3 | `partially_fermented` |
   | 4–6 | `well_fermented` |
   | 7+ | `over_fermented` |
3. **Shoot consistently** — same lighting, same distance, beans filling the frame. This
   matters more than camera quality, because the current baseline keys on colour.
4. **Split by pod, not by photo.** Put every bean from one pod in the same split, or
   near-duplicate images leak between train and test and the accuracy looks fake.

Suggested layout, which you can zip and train on directly:

```
dataset/
├── train/ {unfermented,partially_fermented,well_fermented,over_fermented}/*.jpg
├── val/   {…same four…}/*.jpg
└── test/  {…same four…}/*.jpg
```

### Where to look for existing data

Public cacao fermentation/cut-test datasets do exist and are the fastest way to start —
search **Kaggle**, **Roboflow Universe**, and **Mendeley Data** for *"cacao bean
fermentation stage"* or *"cacao cut test"*. Some Indonesian and Malaysian university
repositories also publish cut-test image sets. Verify the licence and the labelling
method before you rely on one, and always add your own photos from your actual
cooperative, because that is the distribution you will be graded on.

### Training

Any small transfer-learned CNN is enough:

```python
# Python 3.11 or 3.12 (TensorFlow does not yet ship wheels for 3.13/3.14)
base = keras.applications.MobileNetV2(input_shape=(224, 224, 3), include_top=False)
# …GlobalAveragePooling2D → Dense(4, softmax) → compile → fit…
model.save("cacao_model.keras")   # drop into cnn_service/model/
```

Then restart `RUN_CNN.bat` and confirm `GET http://127.0.0.1:8001/health` says
`"engine": "cnn"`.

## Security controls

The document's Part A asks for *"JWT-based authentication issued at login;
role-based authorization; input validation on both client and server; HTTPS for all
client-server and server-service communication."* Here is where each one lives.

### JWT

`backend/auth.py` mints an **HS256** JWT when login or register succeeds:

| Claim | Meaning |
|---|---|
| `sub` | the account's `users.id` |
| `role` | the role the token was minted under |
| `jti` | a random id that is the row in `sessions` |
| `iat` / `exp` | issued-at and expiry (12 hours; `CACAO_JWT_TTL` overrides) |
| `iss` | `cacao-grade-ai` |

The signature and the expiry are checked without touching PostgreSQL, which is what
lets the CNN service scale on its own. The `jti` is then looked up in `sessions`, so
the table acts as a **revocation list**: logging out really kills the bearer instead
of leaving a token that works until it expires. Expired rows are purged at startup.

The account's role is read back from `users` on every request rather than trusted from
the token, so an administrator changing somebody's role takes effect on the very next
call. Passwords are hashed with **PBKDF2-SHA256** at 260,000 iterations with a
per-password salt.

Signing key: set `CACAO_JWT_SECRET` in any shared or deployed environment. Unset, a
key is generated once into `backend/.jwt_secret` so development sessions survive a
restart.

### HTTPS

```bat
backend\make_cert.py        &:: writes certs\cert.pem + certs\key.pem
RUN_CNN_SSL.bat             &:: CNN service -> https://127.0.0.1:8001
RUN_SSL.bat                 &:: backend     -> https://127.0.0.1:8000
```

```bash
cd frontend
flutter run -d chrome --dart-define=CACAO_API=https://127.0.0.1:8000
```

`RUN_SSL.bat` also points the backend→CNN hop at HTTPS and trusts the same
certificate, so *both* hops in the workflow are encrypted and authenticated.
`e2e_test.py` checks this: it asserts the responses arrive over TLS and that the TLS
port **refuses a plaintext request**.

The certificate is self-signed and covers `localhost` plus `127.0.0.1`, so your browser
will warn you once — accept it for localhost. **Do not ship a self-signed certificate
to a public deployment**; use a managed certificate or a TLS-terminating proxy instead.

## When the network drops

The document's Part E names this as the architecture's main risk, and the
post-laboratory reflection spells out what the client must do:

> *"if the inference service or connectivity is unavailable, uploads must be
> **queued or clearly flagged as pending rather than silently lost**."*
>
> *"The Flutter client should detect the failure, cache the pending photo/upload
> locally, show a clear offline/pending status to the user, and automatically
> retry submission once connectivity is restored."*

`frontend/lib/core/pending_uploads.dart` implements exactly that, and the
**Pending Uploads** panel on the farmer's Classify screen is the status it asks
for.

| Requirement | Where it happens |
|---|---|
| **Detect** the failure | `isRetryable()` — no status code (never reached the server), or 502/503/504 (the inference hop behind the API) |
| **Queue** it | `enqueue()` keeps the bytes, batch name, notes and the reason it failed |
| **Cache locally** | the queue is written to `SharedPreferences`, so it is still there after the app is closed and reopened |
| **Show** it | the panel lists every queued photo with its thumbnail, attempt count and last error |
| **Retry automatically** | a 20-second timer replays the queue; **Retry now** does it on demand |
| **Never silently lose** | discard is always the farmer's explicit action, never automatic |

The API makes that distinction possible. `POST /api/classify` answers **400**
when the CNN could not read the photo (replaying it would fail identically
forever, so the client shows it as rejected) and **502/503** when the inference
service itself is failing (worth queueing). `e2e_test.py` checks both.

## Running

Start **both** services (two windows), then the app:

```bat
RUN.bat        &:: backend     -> http://127.0.0.1:8000
RUN_CNN.bat    &:: CNN service -> http://127.0.0.1:8001
```

```bash
cd frontend
flutter run -d chrome
```

> Building the Windows target needs **Developer Mode** enabled (Settings →
> Privacy & security → For developers), because the plugin step requires symlink support.

Set `kApiBaseUrl` in `frontend/lib/core/api_service.dart` if the backend is not on
`http://127.0.0.1:8000` (Android emulator → `http://10.0.2.2:8000`), or override it
without editing code:

```bash
flutter run -d chrome --dart-define=CACAO_API=http://10.0.2.2:8000
```
